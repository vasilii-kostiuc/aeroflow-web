# AeroFlow Web Architecture

## Назначение документа

Документ определяет границы, структуру и правила развития `aeroflow-web`.

Архитектура frontend подчиняется общей архитектуре AeroFlow. Доменные понятия и
правила берутся из `aeroflow-docs`, а публичные операции — из контрактов API.

## Архитектурная роль

`aeroflow-web` является presentation-клиентом. Он помогает пользователю выполнить
use case, но не становится отдельным источником бизнес-решений.

```text
UI
  → frontend use case
  → API client
  → aeroflow-core
  → domain model
```

Frontend может:

* скрывать недоступные действия;
* проверять формат полей до отправки;
* запрашивать подтверждение опасного действия;
* оптимистично обновлять интерфейс там, где это безопасно;
* преобразовывать API DTO в удобную для отображения форму.

Frontend не должен:

* самостоятельно разрешать недопустимый доменный переход;
* считать локальное состояние окончательным результатом операции;
* дублировать агрегаты и доменные сервисы backend;
* связываться с RabbitMQ, базами данных или audio-agent;
* выводить доступ к операции только из скрытой или показанной кнопки.

Авторизация всегда проверяется backend.

## Технологический стек

### React и TypeScript

React отвечает за композицию интерфейса. TypeScript обязателен для исходного кода
приложения и используется в строгом режиме.

API-типы описывают внешний контракт, но не считаются доменными сущностями
frontend.

### Vite

Vite отвечает за development server, сборку и передачу публичной конфигурации
окружения.

### Mantine

Mantine является основной UI-библиотекой:

* layout;
* формы и поля ввода;
* таблицы и визуальные состояния;
* modal и notification;
* theme и responsive UI.

Общие компоненты приложения строятся поверх Mantine только при наличии
повторяющегося поведения или единого продуктового оформления.

### Визуальный язык

Оформление задаётся темой (`app/theme/theme.ts`) и общими компонентами, а не
отдельными экранами (задача 030):

* цвета состояний — только семантические имена темы: `success`, `warning`,
  `danger`, `info`; нейтральное — `gray`, основное действие и выбор — `blue`.
  Конкретную палитру за именем выбирает тема;
* шрифт Inter поставляется с приложением (`@fontsource-variable/inter`), чтобы
  рабочие станции рендерили тот же шрифт, что и разработка;
* шкала заголовков уменьшена под рабочий инструмент; `Badge`, `Paper`, `Table`,
  `Button` получают значения по умолчанию из темы;
* каждый экран начинается с `shared/ui/PageHeader` (заголовок, бейдж, описание,
  действия справа); статус записи справочника — `shared/ui/StatusBadge`.

### TanStack Query

TanStack Query является источником состояния для данных, полученных с сервера:

* списки и детали ресурсов;
* loading и error state;
* кэширование;
* mutations;
* invalidation и refetch;
* согласование параллельных запросов.

Серверные DTO не копируются в Zustand.

Query keys должны быть централизованы в пределах feature:

```ts
const flightDefinitionKeys = {
  all: ['flight-definitions'] as const,
  lists: () => [...flightDefinitionKeys.all, 'list'] as const,
  list: (filters: FlightDefinitionFilters) =>
    [...flightDefinitionKeys.lists(), filters] as const,
  details: () => [...flightDefinitionKeys.all, 'detail'] as const,
  detail: (id: string) => [...flightDefinitionKeys.details(), id] as const,
}
```

После mutation обновляется конкретный кэш или инвалидируются только связанные
query keys.

### Zustand

Zustand используется для небольшого клиентского состояния, которое не принадлежит
серверному API:

* данные текущей клиентской сессии, если они действительно нужны глобально;
* состояние sidebar;
* выбранная тема;
* локальные предпочтения пользователя;
* краткоживущее состояние многошагового UI.

Zustand не используется как универсальный store и не заменяет TanStack Query,
React state или URL.

Если состояние нужно только одному компоненту, используется локальный React
state. Если состояние должно переживать перезагрузку и быть доступно по ссылке,
предпочтителен URL.

### React Router

Router отвечает за:

* дерево экранов;
* layout routes;
* protected routes;
* параметры ресурса;
* query parameters фильтрации и пагинации;
* страницы `not found` и `access denied`.

Фильтры таблиц, поиск, сортировка и номер страницы по возможности хранятся в URL.

## Структура приложения

Рекомендуемая структура ориентирована на продуктовые features:

```text
src/
  app/
    App.tsx
    providers/
    router/
    theme/
  pages/
    login/
    flight-definitions/
    not-found/
  features/
    auth/
    flight-definitions/
  shared/
    api/
    config/
    lib/
    ui/
    types/
  main.tsx
```

### `app`

Композиционный корень приложения:

* подключение providers;
* router;
* QueryClient;
* Mantine theme;
* глобальная обработка ошибок.

`app` не содержит бизнес-specific API calls.

### `pages`

Компонуют законченные экраны из features и shared-компонентов. Страница отвечает
за layout и сценарий экрана, но не содержит низкоуровневый HTTP-код.

### `features`

Каждая feature соответствует пользовательской возможности или устойчивой части
предметного интерфейса.

Пример:

```text
features/flight-definitions/
  api/
    flightDefinitionApi.ts
    flightDefinitionKeys.ts
  model/
    types.ts
    validation.ts
  ui/
    FlightDefinitionForm.tsx
    FlightDefinitionTable.tsx
  hooks/
    useFlightDefinitions.ts
    useCreateFlightDefinition.ts
```

Feature не импортирует код из другой feature напрямую без явной причины.
Повторно используемый нейтральный код переносится в `shared`.

### `shared`

Содержит технические и UI-примитивы без бизнес-сценария:

* HTTP client;
* базовые типы API;
* конфигурацию;
* generic hooks;
* форматирование;
* общие компоненты.

`shared` не импортирует `features` или `pages`.

## Направление зависимостей

```text
app/pages
    ↓
features
    ↓
shared
```

Импорты в обратную сторону запрещены. Циклические зависимости между features
также запрещены.

## API layer

Все HTTP-запросы проходят через единый API client.

Он отвечает за:

* базовый URL;
* JSON headers;
* передачу access token;
* единый разбор успешного ответа;
* преобразование API error в типизированную ошибку;
* одну контролируемую попытку обновления токена;
* отмену исходящих запросов, где это необходимо.

Feature API-функции описывают конкретные endpoints:

```ts
getFlightDefinitions(filters)
getFlightDefinition(id)
createFlightDefinition(input)
updateFlightDefinition(id, input)
activateFlightDefinition(id)
deactivateFlightDefinition(id)
```

React-компоненты не вызывают `fetch` напрямую.

## Аутентификация и токены

`aeroflow-core` является источником истины для пользователя, ролей и срока жизни
сессии.

Базовый поток:

1. пользователь отправляет email и пароль;
2. frontend получает token pair;
3. access token прикладывается к API-запросам;
4. при истечении access token выполняется одна попытка refresh;
5. при неуспешном refresh локальная сессия очищается;
6. пользователь возвращается на страницу входа.

Точный способ хранения refresh token должен быть согласован с backend-контрактом.
Предпочтительный production-вариант — защищённая `HttpOnly Secure SameSite`
cookie. Если текущий API возвращает refresh token в JSON, временное решение и его
риски фиксируются отдельным task.

Нельзя:

* логировать токены;
* помещать токены в URL;
* считать декодированный JWT достаточным доказательством доступа;
* запускать несколько параллельных refresh-запросов.

## Роли

Роль пользователя (задача 033) — `admin`, `dispatcher` или никакой. Web берёт её
из сессии (`user.roles`) и обновляет по `GET /api/v1/me` при старте, фокусе и раз
в минуту: администратор может сменить роль, пока вкладка открыта.

* навигация показывает только доступное роли: диспетчеру — «Панель диспетчера»,
  администратору — всё, включая «Пользователи»;
* маршруты обёрнуты в `RequireRole`: недоступный экран, открытый по ссылке,
  показывает «Нет доступа»;
* стартовая страница по роли: диспетчер — `/dispatcher`, администратор —
  справочники, без роли — «Нет доступа» с просьбой обратиться к администратору;
* всё это — удобство: backend проверяет ту же матрицу на каждый запрос.

Экран «Пользователи» (`/users`, feature `users`): таблица учёток со сменой роли
прямо в строке (`409` «последний администратор» — уведомлением), «Новый
пользователь» (e-mail, пароль, роль) и «Пароль» (задать новый; пользователь
выходит из других сессий). Самостоятельной регистрации нет.

## Состояние системы

Экран «Состояние системы» (`/system-status`, администрирование, feature
`system-status`, задача 034) — компоненты AeroFlow со статусом «Работает /
Внимание / Не работает / Неизвестно» и пояснением, общий итог сверху;
`GET /api/v1/admin/system-status` раз в 10 секунд. При ошибке запроса экран
говорит, что данные могут быть неактуальны.

В панели диспетчера над баннером экстренного режима — `SystemAlertsBanner`:
`GET /api/v1/dispatcher/system-alerts` раз в 15 секунд. Пустой список — баннера
нет; иначе красный баннер «Объявления могут не прозвучать» со списком причин;
если сама проверка не удалась — предупреждение «Состояние системы неизвестно».

## Ошибки

Frontend различает:

* validation errors — показываются рядом с полями;
* authentication errors — завершают или восстанавливают сессию;
* forbidden — показывают отсутствие доступа;
* not found — показывают состояние отсутствующего ресурса;
* conflict — объясняют конфликт бизнес-ключа или состояния;
* network/server errors — показывают возможность повторить запрос.

Компоненты не зависят от сырого формата ошибки транспорта. API client приводит
ошибку к единой модели:

```ts
type ApiError = {
  status: number
  code?: string
  message: string
  violations?: Record<string, string[]>
}
```

Точный тип синхронизируется с фактическим контрактом `aeroflow-core`.

## Формы и валидация

Клиентская валидация повторяет только стабильные ограничения, полезные для UX:

* обязательность поля;
* формат номера рейса;
* формат IATA-кода;
* различие аэропортов отправления и назначения.

Окончательное решение всегда принимает backend. Серверные violations должны
привязываться к соответствующим полям формы.

## Realtime

CRUD первого этапа работает через HTTP.

Для будущей очереди воспроизведения realtime-транспорт выбирается отдельным
решением. Возможные варианты — WebSocket или Server-Sent Events. До фиксации
контракта нельзя строить UI на прямом соединении с `aeroflow-agent`.

При потере realtime-соединения интерфейс должен явно показывать, что данные могут
быть неактуальны.

## Тестирование

Рекомендуемые уровни:

1. unit tests для преобразований, validation и небольших stores;
2. component tests для форм и состояний интерфейса;
3. integration tests features с mock HTTP server;
4. небольшое число end-to-end тестов критических сценариев.

Рекомендуемые инструменты:

* Vitest;
* React Testing Library;
* Mock Service Worker;
* Playwright для end-to-end.

Тесты должны проверять поведение пользователя и публичные контракты, а не
внутреннюю структуру React-компонентов.

## Качество

Минимальные проверки проекта:

```text
lint
typecheck
test
build
```

В production-коде не допускаются:

* необоснованный `any`;
* прямые HTTP-вызовы из UI-компонентов;
* хранение серверных коллекций в Zustand;
* бизнес-правила, расходящиеся с `aeroflow-core`;
* секреты в frontend-конфигурации;
* игнорирование ошибок Promise.

## Первый bounded context

Первый frontend-срез относится к `User Access` и реализует вход, клиентскую
сессию, обновление токенов, защищённые маршруты и выход.

Изменение является presentation/integration-изменением. Оно:

* не добавляет агрегаты;
* не публикует domain events;
* вызывает существующие login, refresh и logout use cases через HTTP API;
* использует Zustand только для состояния клиентской сессии;
* очищает TanStack Query cache при завершении сессии.

Текущий API возвращает refresh token в JSON. До перехода core на
`HttpOnly Secure SameSite` cookie web временно хранит token pair в
`localStorage`. Это осознанный компромисс первого среза, а не целевая
production-модель безопасности.

Второй реализованный frontend-срез относится к `Flight Operations` и предоставляет
административное управление справочником `FlightDefinition` через существующий
HTTP API. Фильтры и пагинация хранятся в URL, server state — в TanStack Query,
создание и редактирование выполняются через modal-форму, а удаление заменено
доменной активацией/деактивацией. Рабочий интерфейс диспетчера для запуска
объявлений на основании активных карточек является отдельным срезом.

Справочник аэропортов является отдельной административной feature внутри
`Flight Operations`. `FlightDefinition` хранит только IATA-коды, а web получает
названия городов из `/api/v1/airports`, использует их в select-полях и отображает
маршруты в формате `Город — Название аэропорта (CODE)`, чтобы различать несколько
аэропортов одного города.

Третий реализованный frontend-срез — панель диспетчера (`/dispatcher`, feature
`dispatcher`). Это рабочий интерфейс запуска рейсовых объявлений, не дублирующий
админку. Доска definition-driven: список строится из активных `FlightDefinition`
(`/api/v1/flight-definitions?active=true`) с наложением статуса текущего
`FlightOccurrence` карточки (`/api/v1/dispatcher/board`); карточка без
occurrence считается «не начата». Операционный день определяет core по часовому
поясу аэропорта (задача 027): поля выбора даты на панели нет, а
`ensure-manual`/`start-next-manual` получают лишь `flightDefinitionId`. Прогон, начатый до полуночи и ещё не доведённый до
финального статуса, остаётся на доске после полуночи с пометкой даты своего
прогона. Доска перезапрашивается поллингом — смена суток и действия с других
рабочих мест подхватываются без перезагрузки. Тип объявления выбирается кнопочным фильтром
(начало/окончание регистрации, посадка, прибытие — `check_in_continuation` не
входит в ручной поток), и список перестраивается под выбранное действие. Запуск
сначала идемпотентно обеспечивает occurrence
(`POST /api/v1/flight-occurrences:ensure-manual`), затем выполняет action-эндпоинт
перехода; eligibility на v1 определяется только по lifecycle-статусу, а
неготовность конфигурации проявляется как `422` у формы. Языки объявления
ограничены настроенными для пары рейс × тип объявления и по умолчанию выбраны все:
коды берутся из `/api/v1/flight-announcement-configs/languages?flightDefinitionId=&announcementType=`
(enabled-варианты enabled-конфига контекста Announcements в порядке `sortOrder`),
человекочитаемые названия — из `/api/v1/languages`. Выбор показан кнопочным
пикером, диспетчер может снять лишние языки; пустой список означает, что для
объявления не настроены языки — показывается подсказка и запуск блокируется.
Стойки и выход — из активных справочников `/api/v1/admin/check-in-counters` и
`/api/v1/admin/gates`.

Панель допускает несколько прогонов одной карточки в день (задача 014) **без
отдельной кнопки**. Карточка, чей последний occurrence достиг финального статуса
цикла (`boarding` для вылета, `arrival_announced` для прилёта), снова становится
eligible под своим первым действием — «Начало регистрации» для вылета и «Прибытие»
для прилёта. Запуск такого действия на отработавшей карточке сначала вызывает
`POST /api/v1/flight-occurrences:start-next-manual` (серверный инкремент
`sequenceNumber`), а затем выполняет action-переход уже на новом occurrence;
обычная (не отработавшая) карточка по-прежнему идёт через `ensure-manual`. Защита
от двойного клика — дизейбл primary-кнопки на время мутации плюс доменный guard:
повторный новый прогон при ещё незавершённом возвращает `409`. Статус карточки
берётся из текущего occurrence карточки — `/dispatcher/board` отдаёт не более
одной записи на карточку.

Панель диспетчера содержит кнопку `Статус` (наследник окна старой САО) — drawer
экрана очереди воспроизведения: секции «Сейчас звучит», «В очереди», «Недавние»
из `GET /api/v1/dispatcher/playback-queue` (read-модель core поверх обратных
событий playback). Данные обновляются поллингом TanStack Query только при
открытом drawer; при ошибке запроса показывается предупреждение о возможной
неактуальности. Ожидающую строку можно убрать из очереди (задача 018): кнопка
«Убрать» с подтверждением зовёт `POST /api/v1/announcements/{id}/cancel`,
инвалидирует query key очереди и полагается на eventual read-модель — строка
переходит в «Недавние» как «Отменено», когда playback подтвердит отмену. Кнопка
есть только у ожидающих строк. Звучащую строку можно остановить (задача 019):
кнопка «Стоп» с подтверждением зовёт
`POST /api/v1/dispatcher/playback-queue/{announcementId}/stop` — Announcement и
рейс не меняются, отменяется только физическое звучание. Как и «Убрать», это
eventual-действие: кнопка есть только у играющей строки, а строка переходит в
«Недавние» как «Прервано» после того, как агент подтвердит остановку и
инвалидация подхватит обновлённую очередь.

Повторяемое объявление (продолжение регистрации) имеет в очереди собственное
нетерминальное состояние `rescheduled` — «ждёт следующего повтора» (задача 023).
Такая строка стоит в секции «В очереди» с подписью времени следующего повтора и
**не** имеет ни «Стоп» (ничего не звучит), ни «Убрать» (серию завершает закрытие
регистрации, а не удаление строки из очереди). Во время самого тика та же строка
показывается в «Сейчас звучит» обычным образом.

Панель диспетчера позволяет запустить дополнительное объявление (задача 024) —
отдельное действие, не строка рейсовой доски. Кнопка «Дополнительное объявление» в
шапке панели открывает модалку с выбором **пресета** и пикером языков. Пресеты —
готовый набор (наследник раздела «Дополнительно» старой САО) из
`GET /api/v1/dispatcher/supplementary-announcements/templates`; при выборе пресета
по умолчанию выбраны все его языки, диспетчер может снять лишние (человекочитаемые
названия — из `/api/v1/languages`). Submit зовёт
`POST /api/v1/dispatcher/supplementary-announcements { templateId, languages }`,
дизейблится на время запроса и инвалидирует query key очереди воспроизведения;
серверные `404/422` (пресет не найден/неактивен, недоступный asset) показываются в
форме. Если пресетов нет — показывается подсказка настроить их в администрировании.
Строка появляется в drawer «Статус» позади рейсовых (приоритет `50`), с
`flightNumber = null` и подписью «Дополнительное объявление»; «Убрать»/«Стоп»
работают как у рейсовой строки, поскольку это обычный `Announcement`.

Панель диспетчера позволяет запустить **экстренное объявление** (задача 026) —
выделенная красная кнопка «Экстренное объявление» в шапке открывает ту же модалку
«пресет + языки», что и дополнительное, с предупреждением о последствиях и кнопкой
«Запустить экстренное»; пресеты приходят из
`GET /api/v1/dispatcher/emergency-announcements/templates`, submit зовёт
`POST /api/v1/dispatcher/emergency-announcements { templateId, languages }`.
Пока экстренный режим активен, в панели висит баннер «Экстренный режим активен» с
кнопкой «Деактивировать экстренный режим» (подтверждение, дизейбл на время запроса,
как у «Стоп»/«Убрать»); состояние баннера берётся из
`GET /api/v1/dispatcher/emergency-announcements/mode` поллингом, а не из факта, что
объявление запустили в этой вкладке, — поэтому баннер верен и для диспетчера,
подключившегося посреди ситуации. Деактивация (`POST
/api/v1/dispatcher/emergency-announcements:deactivate`) eventual: баннер исчезает,
когда playback подтвердит снятие режима. В drawer «Статус» появилось нетерминальное
состояние строки `preempted` — «Прервано экстренным»: объявление не отменено, оно
вернулось в очередь и прозвучит после снятия режима, поэтому строка остаётся в
секции «В очереди» и отличается от терминального «Прервано» (операторский «Стоп»,
задача 019).

Модалка запуска пресета у дополнительного и экстренного объявления — один
компонент (`PresetAnnouncementModal`), параметризованный текстами и мутацией:
выбор пресета и языков одинаков, различается только то, что делает сервер.

Каталогом пресетов управляет отдельная admin-feature `supplementary-templates`
(экран `/supplementary-announcements`, пункт навигации «Дополнительные
объявления»). Таблица показывает название, языки и статус; форма (modal) задаёт
название и языковые варианты — по строке на язык с выбором языка
(`/api/v1/languages`) и аудиофайла (окно выбора из аудиобиблиотеки, см. ниже), с
добавлением/удалением строк и запретом повторяющихся языков. Аудио варианта можно
**выбрать из библиотеки или озвучить прямо в форме**: у каждого варианта есть поле
текста и кнопка «Озвучить», которая зовёт `POST /api/v1/admin/audio-assets:generate`
(TTS, задача 021), подставляет полученный `audioAssetId` в вариант и показывает его
в поле выбора; серверные `422/502` (пустой текст, TTS недоступен) выводятся в форме.
CRUD и активация/деактивация идут на
`/api/v1/admin/supplementary-announcement-templates`; server state — в TanStack
Query, инвалидация по ключу после мутаций.

Каталог экстренных пресетов — feature `emergency-templates` (экран
`/emergency-announcements`, пункт навигации «Экстренные объявления») на тех же
общих компонентах: таблица и форма вынесены в feature `announcement-presets`
(`AnnouncementPresetsScreen`, `AnnouncementPresetForm`),
а `supplementary-templates` и `emergency-templates` остаются тонкими обёртками со
своими api, query-ключами и мутациями. Экраны каталогов идентичны по UX —
дублировать их разметку ради второго эндпоинта было бы лишним.

Аудиобиблиотеку (задача 031) обслуживает feature `audio-assets` — единственный
владелец API assets и папок в web (`/api/v1/admin/audio-assets`,
`/api/v1/admin/audio-folders`): запросы, query-ключи, мутации, сборка дерева папок
из плоского списка и клиентская фильтрация (серверных фильтров пока нет). Другие
features берут из неё публичный `AudioAssetPicker` и хуки, собственных запросов
assets у них нет. Везде в интерфейсе asset называется своим `title`; техническое
имя файла (`name`) — только вторичной строкой.

`AudioAssetPicker` заменяет выпадающий список в сегменте конфигурации рейса и в
варианте пресета. Поле показывает название и язык выбранного asset, кнопку
прослушивания и «Выбрать…»/«Изменить…»; asset, которого нет среди активных,
показан как «Файл недоступен». Кнопка открывает окно библиотеки:

* дерево папок слева («Все файлы», папки, «Без папки») со счётчиками assets
  поддерева с учётом фильтров; на узком экране — select с путями папок;
* «хлебные крошки» открытой папки; в таблице сначала подпапки, затем assets,
  лежащие прямо в папке; в режиме «Все файлы» и при поиске — плоский список с
  колонкой пути папки;
* фильтр языка (по умолчанию язык варианта, «Все языки» показывает остальные с
  бейджем «другой язык»), фильтр источника, поиск по названию и имени файла —
  поиск идёт по всей библиотеке;
* ▶ в каждой строке — файл можно прослушать до выбора; выбор кликом по строке или
  кнопкой «Выбрать»; внутри окна можно загрузить файл (название, язык, папка), и он
  сразу выбирается;
* окно открывается в папке уже выбранного asset, иначе в папке, из которой в
  прошлый раз выбирали в этом месте (ключ места: `segment:<тип объявления>`,
  `preset:supplementary`, `preset:emergency`), иначе на «Все файлы»;
* блок «Недавно использованные» (до 8, новые первыми) — быстрый доступ поперёк
  папок и источников, поэтому учитывает только фильтр языка; при поиске скрыт.

Недавние assets и последняя папка по месту выбора — локальные предпочтения
пользователя: Zustand-store с `persist` в `localStorage`, данные разложены по id
пользователя и не очищаются при выходе. Неактивные ids из недавних вычищаются.

В окне выбора есть и «Новая папка»: папка создаётся в открытой, и окно сразу её
открывает — файл можно загрузить в новую папку, не уходя из редактора.

Экран «Аудиобиблиотека» (`/audio-assets`, пункт навигации «Аудиобиблиотека») —
тот же браузер библиотеки плюс управление:

* у каждой папки в дереве (и у открытой — рядом с «хлебными крошками») меню «⋮»:
  «Новая подпапка», «Переименовать», «Переместить в…», «Удалить» — только пустую,
  с подтверждением; иначе пункт неактивен, серверный `409` — уведомлением.
  Окна папки и «Переместить в…» предлагают только допустимые места: без самой
  папки, её подпапок и мест глубже лимита (та же проверка, что на сервере);
* у файла — меню «⋮»: «Изменить» (название и папка) и «Переместить в…»;
* флажки выбора файлов и «выбрать все» в текущем виде; панель выбранных
  предлагает «Переместить в…» (групповой `POST /api/v1/admin/audio-assets:move`,
  всё или ничего). Выделение сбрасывается при смене папки или фильтров;
* перетаскивание (HTML5 drag and drop, хук `useLibraryDnd`): файл — или все
  выбранные, если тащат выбранный, — на папку в дереве, подпапку в таблице или
  «Без папки»; папка — на другую папку или «Все файлы» (верхний уровень).
  Недопустимые цели не подсвечиваются и не принимают drop; свёрнутая папка под
  курсором раскрывается через ~0,6 с. Перенос оптимистичный (TanStack Query
  `onMutate`) и откатывается с уведомлением при отказе сервера. На сенсорных
  экранах и с клавиатуры перетаскивания нет — для этого «Переместить в…»;
* загрузка файла в открытую папку.

Открытая папка, фильтры и поиск хранятся в URL.

Выбранный/озвученный asset можно **прослушать прямо в браузере**: общий компонент
`shared/ui/AudioPreviewButton` по `audioAssetId` тянет файл с авторизацией
(`GET /api/v1/admin/audio-assets/{id}/file`, `shared/api/apiClient.apiRequestBlob`
→ object URL) и играет через `Audio`. Кнопка есть у вариантов пресета
(feature `supplementary-templates`) и у сегментов конфигурации рейса
(feature `flight-definitions`): в редакторе сегмента рядом с выбором файла, и в
списке сегментов у любого сегмента с готовым asset — как загруженного
`audio_asset`, так и озвученного `text`-сегмента (task 022). У `dynamic_slot` и
`pause` превью нет (нет единого файла). Файл грузится с auth-заголовком (обычный `<audio src>` его не
передаёт), object URL освобождается при остановке/смене asset/размонтировании.
Одновременно во всём приложении звучит не больше одного превью: запуск другого
останавливает предыдущее, а файл, догрузившийся после остановки, не играет.
Строка языкового варианта в режиме просмотра (задача 028) тоже играет свой файл,
если вариант состоит из одного сегмента с готовым asset.

Редактор объявлений рейса (вкладка «Объявления» карточки рейса, задача 028)
устроен как «просмотр по умолчанию, правка по одному». Каждый тип объявления —
вкладка; языковые варианты — строки только для чтения (язык, сводка содержимого,
прослушивание). Включение варианта, перестановка ↑↓ (перенумерация `sortOrder`
затронутых вариантов отдельными `PATCH`) и удаление (с подтверждением)
применяются сразу; тумблер типа объявления — тоже, а интервал повтора сохраняется
кнопкой, активной только при изменении. Язык и сегменты правятся в редакторе,
который открывается на месте строки; одновременно открыт не больше одного
редактора, с одной парой «Сохранить / Отмена». Пока черновик не сохранён,
переключение вкладки типа, навигация внутри приложения (`useBlocker` из
`shared/lib/useUnsavedChangesGuard`, поэтому страница должна жить в data router)
и закрытие вкладки браузера (`beforeunload`) спрашивают подтверждение. API и core
не менялись: экран работает на тех же `PATCH …/announcement-configs/{id}` и
`POST|PATCH|DELETE …/variants`, что и раньше.

## Будущее развитие

Новые экраны добавляются вертикальными срезами:

```text
API contract
  → feature API
  → query/mutation
  → UI scenario
  → tests
```

Frontend не должен заранее вводить модели `FlightSchedule`, `FlightOccurrence`,
`Announcement`, `AudioAsset` или `PlaybackJob`, пока соответствующий use case и
API-контракт не зафиксированы в документации.
